# v0.7.0 — Machine identity, comment authorship and unreleased drafts

Core gains the mechanisms a coding agent needs to participate in a ticket
system without being able to act like a person. Nothing here is agent-specific:
these are general seams, and the product built on them lives in the Enterprise
layer.

## Machine identity

A **service account** belongs to a human owner and carries a **scope set**,
never a role. Tokens are minted with high entropy, stored only as a hash,
compared in constant time, and revoked through the same path that verifies
them — so a caller cannot obtain an identity that skipped a check. The scope
vocabulary is closed: an unknown scope is refused at mint time rather than
silently becoming unenforceable.

**`requireRole` refuses a machine identity outright**, before it reads a role.
This is the load-bearing decision of the release. `requireRole` gates ticket
deletion, role changes and personal-data export; without the refusal, an agent
belonging to a developer would inherit all three. A machine reaches an endpoint
only through an explicit scope check.

Accounts are personal. A developer manages their own and cannot see another's —
reaching for someone else's returns 404, because 403 would confirm it exists.

## Comment authorship

Comments record whether a machine or a person wrote them, derived from the
request identity and never from the request body. A machine cannot post as a
human by passing a field, and a human cannot disclaim a comment by posing as a
machine.

## Unreleased comments

`published_at IS NULL` is a draft: visible to developers, never to the
reporter, regardless of `is_internal`. Publish and discard are developer-only.
The mechanism is general — a person drafting a careful answer wants exactly
this — while the policy of who must review what belongs to a layer above.

A machine that speaks for the support side can never publish something the
reporter will see; core forces the draft. The scope alone did not achieve this,
because `publish` defaults to true and a token used outside the intended tooling
could have answered a customer with nobody's approval.

## Upgrading

Additive only. Two tables, three columns, all guarded. Existing comments are
backfilled as published, so no upgrade hides history from a reporter. An install
that creates no service accounts behaves exactly as before.
