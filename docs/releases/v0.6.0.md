# v0.6.0 — Category language and lightweight intake

Two defects reported from the first live deployment, both in how configurable
categories meet the people using them.

## Category names follow the interface language

Configured categories carried one fixed label per project. A deployment with a
Polish and an Italian storefront therefore showed Italian category names to
anyone who picked the Italian store — including people working in Polish.

The store says what a ticket is about. The language belongs to the person
writing it. Categories now carry a `translations` map, and the frontend
resolves label and description per UI language, field by field, falling back
to the configured default when a language is missing.

The same fix closes a second gap: ticket lists, the board and ticket detail
translated categories through the UI dictionary, so any configured key outside
the built-in five rendered as the raw `category.data_check`. A shared resolver
now serves every one of those views.

## Lightweight categories

A category can declare `simple_intake`. The reporter then gives a title, a
sentence and optionally a file — nothing else. Length thresholds exist so a
report can be worked without follow-up questions; on a question like "can we
add this tag?" they only force padding, and a question that is hard to file is
a question that stays in chat.

Backend and form apply the same relaxed thresholds, so the form never refuses
what the server would accept.

## The form now honours the project's rigour

`require_bug_details` was a project setting the form ignored: it demanded
reproduction steps, expected result, actual result and environment regardless.
A project that had switched the rigour off still could not submit a bug — the
server would have taken it, but the form would not send it.

## Upgrading

Two columns are added to `project_categories` (`translations`, `simple_intake`)
on boot. Existing categories keep their label and stay strict, so an install
that configures nothing sees no change.
